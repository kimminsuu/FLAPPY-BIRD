> FLAPPY-BIRD 프로젝트 개발 과정에서 겪은 주요 시행착오와 이를 통해 얻은 교훈을 정리합니다.

## 1. 인증 시스템 설계 변경 (가장 큰 방향 전환)

### 시행착오
- **초기 계획**: Supabase Auth (이메일/비밀번호) + Kakao 소셜 로그인 + NextAuth.js
- **실제 결과**: 기기 UUID + 닉네임만으로 유저 식별 (로그인 자체 불필요)

### 변경 과정
1. 처음에는 "앱"이니까 로그인이 필요하다고 판단
2. NextAuth.js 설치, Kakao OAuth 연동 코드까지 작성
3. 중간에 "캐주얼 모바일 게임에 로그인이 필요한가?" 재검토
4. **2026-02-14**: Kakao 로그인/NextAuth/랭킹 기능 일괄 삭제
5. 기기 UUID 기반 자동 식별로 전환

### 교훈
- **MVP에서는 최소한의 인증만**: 캐주얼 게임에 복잡한 인증은 유저 이탈 원인
- **"필요할 것 같다"가 아닌 "지금 필요한가"로 판단**: YAGNI 원칙
- **삭제한 코드**: NextAuth 설정, Kakao OAuth callback, 세션 관리 등 → 수백 줄의 불필요한 코드가 사전에 작성됨
- **다음 프로젝트에서**: 인증 방식은 서비스 특성을 먼저 정의한 후 결정할 것

## 2. localStorage → Supabase 마이그레이션

### 시행착오
- 개발 초기(1/17~2/19)에는 모든 데이터를 localStorage에 저장
  - 유저 정보, 코인, 보유 새, 스테이지 기록, 계절 테마 등
- **2026-02-20**: Phase 2에서 전체를 Supabase로 일괄 전환
- 변환 대상 파일: 6개 화면 컴포넌트 + 2개 Context + 1개 서비스

### 문제점
- localStorage 기반으로 이미 완성된 로직을 전부 뜯어고침
- 동기(localStorage) → 비동기(Supabase API) 전환으로 모든 데이터 접근 패턴 변경
- `JSON.parse(localStorage.getItem(...))` → `await supabase.from(...).select(...)` 일괄 교체
- 컴포넌트마다 loading 상태 추가 필요

### 교훈
- **DB 연동은 최대한 일찍**: 프로토타입이라도 기본 CRUD 구조를 Supabase로 시작했으면 마이그레이션 비용 절감
- **데이터 접근 레이어 분리**: `user-service.ts` 하나에 모든 CRUD를 집중시킨 것은 좋은 판단이었음. localStorage든 Supabase든 서비스 레이어만 교체하면 되는 구조
- **다음 프로젝트에서**: Day 1부터 Supabase(또는 선택한 DB)로 시작. localStorage는 캐시/폴백용으로만 사용

## 3. 게임 엔진 아키텍처 (game-page.tsx 비대화)

### 시행착오
- 게임 엔진을 단일 파일(`game-page.tsx`)에 구현
- **최대 1,911줄**까지 비대해짐 (전체 코드의 32%)
- 게임 루프, 렌더링, 물리, 입력, 아이템, 스테이지 로직이 하나의 `useCallback` 안에 혼재
- **2026-02-25 (커밋 88dd7fa)**: 5개 모듈로 분리 리팩토링
  - `game-types.ts` (상태/타입)
  - `game-actions.ts` (게임 로직)
  - `stage-spawner.ts` (스테이지 생성)
  - `game-renderer.ts` (캔버스 렌더링)
  - `game-over-handler.ts` (종료 처리)
  - `game-page.tsx`는 1,911 → 737줄로 축소

### 문제점
- 리팩토링 전에는 특정 로직 수정 시 1,900줄 파일에서 해당 위치를 찾아야 했음
- Claude의 컨텍스트 윈도우도 빠르게 소모 (매번 전체 파일 읽기)
- 스테이지 추가 시마다 같은 파일에 조건문이 누적

### 교훈
- **게임 엔진은 처음부터 모듈 분리**: 렌더링/로직/입력/상태를 분리하는 것이 표준
- **파일 500줄 이상이면 분리 신호**: 특히 AI 보조 개발에서는 컨텍스트 효율에 직결
- **다음 프로젝트에서**: ECS(Entity-Component-System) 패턴 또는 최소한 관심사 분리를 Day 1부터 적용

## 4. 모바일 성능 최적화 (프레임 드롭)

### 시행착오
- 개발 중 PC 브라우저에서는 문제없이 동작
- Samsung S23에서 테스트 시 프레임 드롭 발생 (특히 파이프/포탈 밀집 구간)
- 원인 분석:
  - `ctx.save()/restore()` 과다 호출
  - 파이프 바디 세그먼트마다 개별 `beginPath/stroke`
  - `Array.splice()` 매 프레임 호출 (O(n) 시프트)
  - DPR 2.0으로 픽셀 수 4배
  - `setScore()` 매 프레임 React 리렌더

### 적용한 최적화
| 항목 | Before | After |
|------|--------|-------|
| 파이프 렌더링 | 세그먼트마다 beginPath | 배치 beginPath+stroke |
| save/restore | 모든 오브젝트마다 | translate/-translate로 대체 |
| 배열 삭제 | splice(i, 1) | swap-and-pop |
| DPR | Math.min(dpr, 2) | Math.min(dpr, 1.5) |
| setScore | 매 프레임 | 값 변경 시에만 (prevScoreRef) |

### 교훈
- **모바일 테스트는 일찍, 자주**: PC에서 잘 되는 것은 모바일 성능을 보장하지 않음
- **Canvas 최적화 원칙**: batch draw call, minimize state change, reduce pixel count
- **다음 프로젝트에서**: 개발 초기부터 타겟 디바이스에서 주기적으로 성능 프로파일링

## 5. 사운드 시스템 반복 수정

### 시행착오
- 파괴(break) 아이템 효과음을 3번 수정
  1. 첫 버전: 화이트 노이즈 + 밴드패스 필터 → "맘에 안들어"
  2. 두번째: 볼링 스트라이크 느낌 → "유리/얼음 느낌으로"
  3. 세번째: 하이패스 노이즈 + 사인파 파편 → 최종 채택

### 교훈
- **사운드는 주관적**: 텍스트 설명("파사삭")과 실제 구현의 갭이 큼
- **빠른 이터레이션이 핵심**: Web Audio API로 코드만으로 합성하니 수정이 즉각적
- **다음 프로젝트에서**: 사운드는 레퍼런스(참고 음원)를 먼저 공유받고 구현

## 6. 개발 서버 관리 실수

### 시행착오
- `npm run dev` 프로세스를 TaskStop으로 중지했으나 실제 Node 프로세스가 살아있음
- `.next/dev/lock` 파일이 남아 새 서버 시작 불가
- 코드 수정이 반영 안 되는 것으로 착각 (실제로는 구 서버가 캐시된 코드를 서빙)

### 해결
```bash
taskkill //F //PID <old-pid>
rm -f .next/dev/lock
npm run dev
```

### 교훈
- **프로세스 정리 확인**: 서버 재시작 시 이전 프로세스 종료 확인 필수
- **변경 미반영 시**: 코드 문제가 아니라 서버/캐시 문제일 수 있음

## 7. 스테이지 기믹 설계의 점진적 복잡도

### 잘한 점
- Stage 1-2: 기본 파이프만 (튜토리얼)
- Stage 3-4: 텔레포트 도입 (새 메카닉 1개)
- Stage 5-6: 중력 반전 + 혼합 (메카닉 조합)
- Stage 7-8: 스피드 링 (속도 변화)
- Stage 9: 시련 (종합)

### 교훈
- **기믹은 하나씩 도입 후 조합**: 유저 학습 곡선을 고려한 점진적 난이도 설계가 효과적
- **데이터 드리븐 설계**: `stages.ts`에 파이프 배치를 데이터로 관리한 것이 스테이지 추가를 용이하게 함
