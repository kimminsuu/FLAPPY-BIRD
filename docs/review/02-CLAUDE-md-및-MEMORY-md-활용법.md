# 02. CLAUDE.md 및 MEMORY.md 활용법 분석

> AI 보조 개발에서 프로젝트 문서(CLAUDE.md)와 세션 간 기억(MEMORY.md)을 어떻게 활용했는지 분석하고, 개선 방향을 제시합니다.

---

## 1. CLAUDE.md 활용 분석

### 현재 구성 (최종 버전 기준)

| 섹션 | 줄 수 (약) | 역할 |
|------|-----------|------|
| Project Overview | 5줄 | 프로젝트 한줄 설명 |
| Tech Stack | 30줄 | 기술 스택 명시 |
| TODO List | 50줄 | 진행/완료 상태 추적 |
| 배포 Phase 계획 | 60줄 | 인증/배포 단계별 계획 |
| Agent Types | 30줄 | AI Agent 실행 전략 |
| Screens | 30줄 | 화면 구성 + 네비게이션 플로우 |
| Project Structure | 100줄+ | 폴더/파일 트리 + 역할 설명 |
| Commands | 15줄 | 빌드/실행 명령어 |
| Workflow | 30줄 | 브랜치 전략 + 작업 흐름 |
| Notes | 50줄+ | 모델 선택, Context7, 모바일 고려사항 |

### 잘한 점

#### (1) Project Structure가 가장 유용했음
- 파일별 한줄 설명이 있어서 AI가 "어떤 파일을 수정해야 하는지" 즉시 파악
- 새 파일 추가 시 여기도 업데이트하는 규칙을 세운 것이 효과적
- **예시**: "일일 보상 기능 추가" → CLAUDE.md에서 `daily-reward-modal.tsx` 위치와 역할 즉시 확인

#### (2) TODO List로 프로젝트 진행 상황 공유
- 완료/진행중/대기 상태가 명확 → AI가 현재 맥락을 빠르게 이해
- "다음 할 일" 질문 없이도 자연스럽게 작업 진행

#### (3) Navigation Flow 다이어그램
```
HomeScreen ←→ BirdSelectionScreen
    ↓
ModeSelectionScreen
    ├── RECORD MODE → GameScreen
    └── STAGE MODE  → StageSelectScreen → GameScreen
```
- 화면 간 관계를 ASCII로 표현 → AI가 라우팅 구조를 즉시 이해

### 개선할 점

#### (1) CLAUDE.md가 너무 길어짐 (~400줄)
- **문제**: 매 대화 시작 시 전체가 컨텍스트에 로드됨 → 토큰 소모
- **해결**: 핵심 정보만 CLAUDE.md에 유지, 상세 내용은 별도 파일로 분리
  ```
  CLAUDE.md (100줄 이내)
  ├── docs/architecture.md  ← Project Structure 이동
  ├── docs/conventions.md   ← 코딩 규칙 이동
  └── docs/deployment.md    ← 배포 계획 이동
  ```

#### (2) 완료된 항목이 계속 남아있음
- TODO List의 Completed 섹션이 30줄+ → 더 이상 필요 없는 정보
- **해결**: 완료 항목은 주기적으로 별도 파일(`docs/changelog.md`)로 이동

#### (3) 중복 정보
- 배포 Phase 계획의 인증 방식 변경 히스토리가 여전히 남아있음
- 이미 결정된 사항("기기 UUID 사용")만 남기고 과거 히스토리는 제거

#### (4) 모델 선택 가이드의 실효성
- "이 작업은 [작업 유형]이므로 **[모델]** 추천합니다" 규칙
- 실제로는 사용자가 이미 모델을 결정한 상태에서 작업 요청 → 매번 추천 메시지가 불필요한 오버헤드
- **해결**: 모델 추천은 복잡한 설계 작업 시에만 선택적으로 제안

## 2. MEMORY.md 활용 분석

### 현재 구성

| 항목 | 역할 | 유용성 |
|------|------|--------|
| 파일 주석 규칙 | JSDoc 상단 주석 관리 | ★★★★★ |
| 보안 점검 | security-review.md 링크 | ★★★☆☆ |
| 다음 작업 | Next Up 태스크 | ★★★★☆ |
| (i) 모달 업데이트 규칙 | 기능 추가 시 설명 모달 갱신 | ★★★★★ |
| Agent 실행 전략 | 커밋/PR 시점 에이전트 실행 | ★★★☆☆ |
| Android 빌드 절차 | APK 빌드+설치 명령어 | ★★★★★ |
| 토큰 절약 규칙 | gradlew -q, 배치 읽기 등 | ★★★★☆ |

### 잘한 점

#### (1) Android 빌드 절차가 가장 높은 ROI
- 5단계 빌드+설치 프로세스를 한번 기록 → 이후 매번 참조
- `JAVA_HOME`, `adb` 전체 경로 등 매번 검색해야 할 정보를 영구 보관
- **절약 효과**: 매 빌드마다 ~2분 탐색 시간 절약 × 20회 이상 = 40분+

#### (2) 파일 주석 규칙이 코드 품질 유지에 기여
- "작업 전 주석 읽기 → 작업 후 주석 업데이트" 루틴
- AI가 파일 역할을 오해하고 잘못된 코드를 삽입하는 것을 방지

#### (3) 토큰 절약 규칙이 실제 비용 절감
- `gradlew -q`: Gradle Task 로그 수천 줄 → 0줄
- "Grep 우선, 해당 영역만 Read": 1,900줄 파일 전체 읽기 회피

### 개선할 점

#### (1) 세션 종료 시 "다음 작업" 업데이트 미흡
- "다음 작업" 항목이 오래된 상태로 방치되는 경우 있음
- **해결**: 매 세션 종료 시 "다음 작업" 리스트 갱신을 루틴화

#### (2) 트러블슈팅 기록 부재
- dev 서버 lock 파일 문제, 프로세스 충돌 등 반복 가능한 이슈가 기록되지 않음
- **해결**: `memory/troubleshooting.md` 파일 추가

#### (3) 구조가 단순 리스트
- 현재 플랫한 마크다운 리스트 구조
- 주제별로 분리하면 검색 효율 향상
  ```
  memory/
  ├── MEMORY.md          ← 인덱스 (200줄 이내)
  ├── build-commands.md  ← Android 빌드
  ├── conventions.md     ← 코딩 규칙
  └── troubleshooting.md ← 트러블슈팅
  ```

## 3. 다음 프로젝트를 위한 CLAUDE.md 템플릿

```markdown
# Project Overview
(프로젝트 한줄 설명, 플랫폼, 핵심 기술)

# Tech Stack
(확정된 기술만 간결하게)

# Project Structure
(파일 트리 + 한줄 설명, 이것이 가장 중요)

# Commands
(빌드, 테스트, 배포 명령어)

# Current TODO
(진행중/대기 항목만, 완료는 별도 파일)

# Conventions
(코딩 규칙, 브랜치 전략, 커밋 규칙 — 핵심만)

# Notes
(특이사항, 주의점)
```

**목표**: 100줄 이내. 상세 정보는 `docs/` 하위에 분리.

## 4. 다음 프로젝트를 위한 MEMORY.md 가이드

### 저장해야 할 것
- **반복 명령어**: 빌드, 배포, 테스트 등 매번 실행하는 명령 체인
- **코딩 컨벤션**: 파일 주석 규칙, 네이밍 등 일관성이 필요한 규칙
- **환경 이슈**: OS별 경로, 환경변수, 도구 버전 등 환경 종속적 정보
- **유저 선호도**: "항상 bun 사용", "커밋 메시지 한국어" 등

### 저장하지 말아야 할 것
- **현재 작업 상태**: "지금 XX 구현 중" → 세션 컨텍스트로 충분
- **일회성 정보**: 특정 버그의 일시적 워크어라운드
- **CLAUDE.md와 중복**: 이미 프로젝트 문서에 있는 내용

### 구조화 원칙
- **200줄 이내**: 넘으면 주제별 파일로 분리
- **검색 가능하게**: 키워드 중심 제목, grep으로 찾을 수 있는 형태
- **주기적 정리**: 매 10세션마다 불필요한 항목 삭제
