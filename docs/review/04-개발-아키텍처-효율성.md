# 04. 개발 아키텍처 효율성 분석

> 프로젝트의 기술 스택 선택, 폴더 구조, 코드 아키텍처가 효율적이었는지 분석합니다.

---

## 1. 기술 스택 평가

### Next.js (App Router) — 게임 앱에 적합했는가?

| 항목 | 평가 | 설명 |
|------|------|------|
| 라우팅 | ★★★★☆ | App Router의 파일 기반 라우팅이 6개 화면 관리에 편리 |
| SSR/SSG | ★★☆☆☆ | 게임 앱에서 서버 사이드 렌더링의 이점이 거의 없음 |
| 번들 크기 | ★★★☆☆ | React + Next.js 오버헤드가 Canvas 게임에는 과도 |
| 개발 경험 | ★★★★★ | Turbopack HMR, TypeScript 지원 우수 |
| 모바일 패키징 | ★★★☆☆ | Capacitor와 통합 가능하나 `output: 'export'` 필요 |

**결론**: Next.js는 UI 화면(홈, 새 선택, 모드 선택 등)에는 적합하지만, Canvas 게임 엔진에는 과도한 프레임워크. 다만 "하나의 기술 스택으로 전체 앱을 구현"한다는 측면에서는 효율적 선택.

**대안 검토**:
- **Vite + React**: SSR 불필요 시 더 가벼운 선택
- **Phaser.js**: 게임 전용 프레임워크, 하지만 UI 화면 구현이 약함
- **현실적 판단**: Next.js 선택은 "합리적 트레이드오프"였음

### Supabase — 적합했는가?

| 항목 | 평가 | 설명 |
|------|------|------|
| 설정 용이성 | ★★★★★ | 프로젝트 생성 → 테이블 → RLS까지 1일 완료 |
| 무료 티어 | ★★★★★ | 1,000유저까지 $0/월 |
| JS 클라이언트 | ★★★★☆ | `supabase-js`가 직관적 |
| RLS 정책 | ★★★☆☆ | device_id 기반 RLS가 아직 미구현 (보안 이슈) |
| 실시간 기능 | 미사용 | 랭킹 등에 활용 가능하지만 현재 불필요 |

**결론**: 캐주얼 게임 백엔드로 Supabase는 최적의 선택. 별도 서버 없이 직접 DB 접근.

### Capacitor — 적합했는가?

| 항목 | 평가 | 설명 |
|------|------|------|
| 웹→모바일 변환 | ★★★★☆ | 코드 변경 없이 APK 생성 가능 |
| 성능 | ★★★☆☆ | WebView 기반이라 네이티브 대비 성능 약간 저하 |
| 빌드 프로세스 | ★★☆☆☆ | 5단계 수동 빌드 체인 (MEMORY.md에 기록할 정도로 복잡) |

## 2. 폴더 구조 평가

### 현재 구조의 강점

```
app/          → 라우팅 전용 (thin layer)
components/   → UI 컴포넌트
lib/          → 비즈니스 로직
types/        → 타입 정의
```

**좋은 점**:
- `app/` 폴더가 라우팅 역할만 담당 → 각 `page.tsx`가 5~20줄로 매우 가벼움
- 비즈니스 로직(`lib/`)과 UI(`components/`)가 명확히 분리
- `types/` 폴더로 타입 정의 중앙화

### 현재 구조의 약점

#### (1) components/ 가 플랫함
```
components/
├── ui/                     ← 공통 UI (5개 파일)
├── login-page.tsx          ← 페이지 컴포넌트
├── home-page.tsx
├── bird-selection-page.tsx
├── mode-selection-page.tsx
├── stage-select-page.tsx
├── game-page.tsx
└── daily-reward-modal.tsx
```

- 페이지 컴포넌트와 공통 UI가 같은 레벨에 혼재
- 모달, 폼 등 하위 컴포넌트가 페이지 파일에 인라인으로 작성됨

**개선안**:
```
components/
├── ui/           ← 공통 UI
├── pages/        ← 페이지 컴포넌트
│   ├── home/
│   │   ├── HomePage.tsx
│   │   └── NicknameModal.tsx
│   ├── game/
│   │   ├── GamePage.tsx
│   │   ├── GameOverModal.tsx
│   │   └── ClearModal.tsx
│   └── ...
└── modals/       ← 공통 모달
```

#### (2) lib/game/ 분리가 늦었음
- game-page.tsx가 1,911줄이 된 후에야 `lib/game/` 모듈로 분리
- 초기부터 게임 엔진을 별도 모듈로 설계했으면 리팩토링 비용 절약

## 3. 코드 아키텍처 패턴 평가

### Context API 활용 — 적절했는가?

| Context | 역할 | 평가 |
|---------|------|------|
| UserContext | 유저 상태 (닉네임, 코인, 보유 새) | ★★★★☆ |
| SeasonContext | 계절 테마 상태 | ★★★★★ |

**잘한 점**:
- 글로벌 상태가 2개뿐이므로 Redux/Zustand 없이 Context로 충분
- `UserProvider`에서 device UUID 자동 로드 → 인증 로직 중앙화

**아쉬운 점**:
- `UserContext`가 너무 많은 책임: 닉네임 + 코인 + 보유 새 + 스테이지 기록
- 코인 차감/충전 시 전체 Context 리렌더

### 데이터 서비스 레이어 — user-service.ts

```typescript
// 모든 Supabase CRUD를 한 파일에 집중
export async function createUser(deviceId, nickname) { ... }
export async function updateCoins(userId, amount) { ... }
export async function getUserBirds(userId) { ... }
export async function saveStageRecord(userId, stageId, score) { ... }
// ... 15개+ 함수
```

**잘한 점**:
- 데이터 접근 로직이 한 곳에 집중 → localStorage → Supabase 전환 시 이 파일만 수정
- 컴포넌트가 Supabase 직접 호출하지 않음 → 관심사 분리

**아쉬운 점**:
- 파일이 점점 커짐 → 도메인별 분리 고려 (user-service, bird-service, stage-service)

### Canvas 게임 렌더링 — 직접 구현

**잘한 점**:
- Canvas 2D API 직접 사용으로 외부 의존성 없음
- requestAnimationFrame 기반 게임 루프 → 표준 패턴

**아쉬운 점**:
- 오브젝트 풀링 미적용 (파이프, 아이템을 매번 new Object)
- 더블 버퍼링 미적용 (오프스크린 캔버스 미사용)
- ECS 패턴 미적용 → 엔티티-로직 결합

## 4. 데이터 흐름 평가

### 현재 데이터 흐름
```
Supabase DB
    ↕ (supabase-js REST)
user-service.ts (CRUD 레이어)
    ↕
UserContext (React Context)
    ↕
Components (UI)
```

**장점**: 단순하고 이해하기 쉬움
**단점**: 캐싱 전략 부재 → 매번 DB 호출

### 개선 가능한 패턴
```
Supabase DB
    ↕
user-service.ts + React Query (캐시 + 자동 갱신)
    ↕
Components
```
- React Query(TanStack Query) 도입 시: 자동 캐싱, stale-while-revalidate, 낙관적 업데이트

## 5. 확장성 평가

### 현재 구조로 확장 가능한 것
- 새 스테이지 추가: `stages.ts`에 데이터 추가만으로 가능 → ★★★★★
- 새 새(Bird) 추가: `birds.ts`에 데이터 + 이미지 추가 → ★★★★★
- 새 아이템 타입 추가: game-actions.ts 수정 필요 → ★★★☆☆
- 새 화면 추가: app/ 라우트 + components/ 컴포넌트 → ★★★★☆

### 확장에 어려운 부분
- 멀티플레이어: 현재 아키텍처로는 불가 (서버 사이드 게임 로직 필요)
- 실시간 랭킹: Supabase Realtime 추가 필요
- 복잡한 게임 기믹: 현재 if-else 분기로 처리 → 기믹 수 증가 시 복잡도 폭증
